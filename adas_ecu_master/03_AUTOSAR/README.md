## 3.2 Software Components (SWC) — How Your Code Plugs In

```
An SWC is your application code packaged as an AUTOSAR component.

SWC has:
  Ports (data flow):
    - Sender/Receiver Port: for signals/data (e.g., vehicle speed from BCM)
    - Client/Server Port:   for service calls (e.g., NvM write)
  
  Runnables:
    - C functions that the RTE calls at configured intervals
    - Example: LKA_Main() is a runnable called every 10ms
    
  Internal State:
    - Variables local to the SWC (not accessible to other SWCs directly)
```

### LKA SWC Example

```c
/* LKA SWC Interface (ARXML-generated, do NOT edit by hand)
 * This header is auto-generated by tools like Vector DaVinci, EB tresos, ETAS ISOLAR
 */

// Rte_LkaSwc.h (auto-generated)
// Port: LaneDataIn  — receive lane offset from camera SWC
Std_ReturnType Rte_Read_LKA_LaneDataIn_LaneOffset(float32* value);
Std_ReturnType Rte_Read_LKA_LaneDataIn_LaneConfidence(uint8* confidence);

// Port: VehicleDataIn — receive speed from BCM SWC
Std_ReturnType Rte_Read_LKA_VehicleDataIn_VehicleSpeed(float32* speedKph);

// Port: SteeringOut — send steering request to EPS SWC
Std_ReturnType Rte_Write_LKA_SteeringOut_TorqueRequest(float32 torqueNm);
Std_ReturnType Rte_Write_LKA_SteeringOut_LkaModeActive(boolean active);

// Runnable: LKA_Main (called every 10ms by OS)
void LKA_MainRunnable(void);
```

```c
/* LkaSwc.c — YOUR implementation (hand-coded) */

#include "Rte_LkaSwc.h"
#include "LkaController.h"

/* SWC internal state — static, no heap */
static LkaController g_lkaController;
static boolean       g_lkaInitDone = FALSE;

/* Runnable: called at startup by RTE */
void LKA_InitRunnable(void) {
    LkaController_Init(&g_lkaController);
    g_lkaInitDone = TRUE;
}

/* Runnable: called every 10ms by OS */
void LKA_MainRunnable(void) {
    if (!g_lkaInitDone) { return; }

    /* Read inputs via RTE (decoupled from CAN implementation) */
    float32 laneOffset    = 0.0F;
    float32 vehicleSpeed  = 0.0F;
    uint8   laneConfidence = 0U;

    Rte_Read_LKA_LaneDataIn_LaneOffset(&laneOffset);
    Rte_Read_LKA_LaneDataIn_LaneConfidence(&laneConfidence);
    Rte_Read_LKA_VehicleDataIn_VehicleSpeed(&vehicleSpeed);

    /* Run control algorithm */
    LkaInputs inputs = {laneOffset, laneConfidence, vehicleSpeed};
    LkaOutputs outputs = LkaController_Process(&g_lkaController, &inputs);

    /* Write outputs via RTE */
    Rte_Write_LKA_SteeringOut_TorqueRequest(outputs.steeringTorqueNm);
    Rte_Write_LKA_SteeringOut_LkaModeActive(outputs.isActive);
}
```

## 3.3 COM Stack — How CAN Signals Reach Your SWC

```
CAN Bus → CAN Driver (CanDrv, MCAL) 
        → CAN Interface (CanIf)
        → CAN Transport Layer (CanTp, for UDS/multi-frame)
        → PDU Router (PduR)  ─── routes PDUs to COM or TP
        → COM (Signal layer)
        → RTE (distributes signals to SWCs)
        → Your SWC via Rte_Read_*

Key concepts:
  PDU (Protocol Data Unit): a CAN frame as seen by COM stack
  I-PDU: Interaction-Layer PDU (what COM works with)
  Signal: individual value within a PDU (e.g., VehicleSpeed = bits 0-15 of PDU 0x100)
  
  COM configuration (in ARXML):
    ComSignal:  VehicleSpeed
      ComBitPosition:   0
      ComBitSize:       16
      ComSignalType:    UINT16
      ComFactor:        0.01
      ComOffset:        0
      ComIPduRef:       BCM_Status_0x100
```

## 3.4 DEM (Diagnostic Event Manager) — Fault Logging

```c
/* Logging a fault in AUTOSAR DEM */

/* DEM event IDs are defined in Dem_Cfg.h (auto-generated) */
#define DEM_EVENT_ID_LKA_CAMERA_TIMEOUT      0x0001U
#define DEM_EVENT_ID_LKA_STEERING_FAILURE    0x0002U
#define DEM_EVENT_ID_ACC_RADAR_SIGNAL_LOST   0x0003U

/* Report fault detected */
void reportSensorTimeout(void) {
    /* Report failed event to DEM */
    /* DEM stores it in NvM as DTC with timestamp and occurrence counter */
    Dem_ReportErrorStatus(DEM_EVENT_ID_LKA_CAMERA_TIMEOUT, 
                          DEM_EVENT_STATUS_FAILED);
}

/* Report sensor recovered */
void reportSensorRecovered(void) {
    Dem_ReportErrorStatus(DEM_EVENT_ID_LKA_CAMERA_TIMEOUT,
                          DEM_EVENT_STATUS_PASSED);
}

/* DEM stores in NvM: 
   DTC 0x012301 (mapped from event ID)
   Status: 0x09 (TestFailed + ConfirmedDTC)
   Timestamp: 0x1A2B3C4D (operating hours)
   OccurrenceCounter: 3
   FreezeFrame: {VehicleSpeed=50.2, Timestamp=12345}
*/
```

## 3.5 AUTOSAR Adaptive — Key Differences

```
AUTOSAR Classic:  Static, compile-time. Microcontrollers. Fixed task table.
AUTOSAR Adaptive: Dynamic, service-oriented. Linux/QNX. Runtime discovery.

Adaptive uses:
  - SOME/IP service discovery
  - ara::com (communication API)
  - ara::exec (execution management)  
  - C++14/17, STL allowed

Example: Adaptive service (not compiled into single image — separate processes):

// In service provider (Camera Perception AA):
class CameraPerceptionSkeleton : public ara::com::Skeleton {
public:
    // Event: sent when new frame is processed
    ara::com::SamplePtr<LaneDetectionResult> laneDetected;
    
    void offerService() {
        // Registers with SOME/IP service discovery
    }
};

// In service consumer (LKA AA):
class LkaProxy : public ara::com::Proxy {
public:
    // Subscribe to lane detection event
    void subscribeLaneDetection() {
        camera_proxy_.laneDetected.Subscribe(
            [this](const LaneDetectionResult& result) {
                onLaneDataReceived(result);
            }
        );
    }
};
```

## 3.6 Interview Questions

```
L1:
  Q: What is the RTE in AUTOSAR?
  A: Runtime Environment. Auto-generated middleware that decouples SWCs from each other
     and from BSW. SWCs communicate ONLY through the RTE via Rte_Read/Rte_Write/Rte_Call.
     This means you can swap an SWC implementation without changing other SWCs.
     The RTE is generated from ARXML configuration using tools like DaVinci or ISOLAR.

  Q: What is the difference between SWC and BSW in AUTOSAR?
  A: SWC (Software Component): application code you write. Implements ADAS features.
     Communicates via RTE ports. Platform-independent.
     BSW (Basic Software): platform-provided services (CAN, Diagnostics, NvM, OS).
     Configured by tool but NOT written by application developer (you).
     SWC uses BSW services through standardised interfaces.

L2:
  Q: What is the COM stack and how does a CAN signal reach your SWC?
  A: CAN Driver (MCAL) receives the raw frame from hardware.
     CanIf routes it to the PDU Router.
     COM unpacks the signal from the PDU based on ARXML configuration (bit position, size, factor).
     COM makes the signal available in a buffer.
     RTE reads from COM buffer when your runnable calls Rte_Read_*().
     No direct CAN access from SWC — fully decoupled.

  Q: What is a runnable and how does it get triggered?
  A: A runnable is a function within an SWC that performs one task cycle of processing.
     It is mapped to an OSEK task and triggered by the OS at the configured period.
     The ARXML defines: runnable name, period, required resources.
     OS task scheduling ensures timing. Multiple runnables can share a task.

L3:
  Q: Explain the difference between AUTOSAR Classic and AUTOSAR Adaptive.
  A: Classic: static architecture, compile-time. All components in one binary.
     Designed for microcontrollers (no OS with MMU). OSEK OS. No heap.
     Used for: body control, powertrain, sensor processing.
     
     Adaptive: dynamic service-oriented architecture. Multiple processes.
     Requires Linux/QNX with MMU. C++14/17. Service discovery (SOME/IP).
     Used for: ADAS fusion, high-performance compute, OTA, V2X.
     
     Modern ADAS ECUs use BOTH: Adaptive for perception/planning on high-compute
     domain controller; Classic for actuator ECUs (EPS, brakes).
```
