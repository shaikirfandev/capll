# Test Execution Guide
## TCU Validation Framework v2.0.0

---

## 1. Overview

The test suite is divided into three tiers:

| Tier | Binary | Timeout | Label | Purpose |
|------|--------|---------|-------|---------|
| Unit | `unit_tests` | 60 s | `unit` | Class-level, no hardware |
| Integration | `integration_tests` | 120 s | `integration` | Multi-module, vcan0 |
| Stress | `stress_tests` | 600 s | `stress` | Load, throughput, concurrency |

---

## 2. Quick Start

```bash
# Build (Debug with tests)
scripts/build.sh

# Setup virtual CAN
scripts/setup_vcan.sh

# Run all tests
scripts/run_tests.sh
```

---

## 3. Individual Test Execution

### Unit tests
```bash
build/Debug/bin/unit_tests
```

### Integration tests
```bash
build/Debug/bin/integration_tests
```

### Stress tests (takes up to 10 min)
```bash
build/Debug/bin/stress_tests
```

### Run a specific test
```bash
build/Debug/bin/unit_tests --gtest_filter="CANManagerTest.SendFrame"
```

### Run a specific test suite
```bash
build/Debug/bin/unit_tests --gtest_filter="ConfigManagerTest.*"
```

### List all available tests
```bash
build/Debug/bin/unit_tests --gtest_list_tests
```

## 4. CTest Integration

After building, use CTest for a unified view:

```bash
cd build/Debug
ctest --output-on-failure           # Run all suites
ctest -L unit --output-on-failure   # Only unit tests
ctest -L integration -V             # Integration, verbose
ctest --parallel 2                  # Parallel execution
```

## 5. XML Test Reports

GoogleTest produces JUnit-compatible XML reports:

```bash
build/Debug/bin/unit_tests \
    --gtest_output=xml:reports/unit_tests.xml

build/Debug/bin/integration_tests \
    --gtest_output=xml:reports/integration_tests.xml
```

These are automatically generated by `scripts/run_tests.sh` under `reports/`.

## 6. HTML / JSON / CSV Reports

The `ReportGenerator` produces rich reports from `TestSuiteResult` objects.  
Reports are generated at the end of every `tcu_validator` run:

```
reports/
├── tcu_validation_report.html     ← Human-readable dark-theme dashboard
├── tcu_validation_report.json     ← Machine-parseable structured data
└── tcu_validation_report.csv      ← Import into Excel / Jira
```

Change the output directory:
```bash
./bin/tcu_validator \
    --config configs/default.json \
    --output /path/to/custom/reports \
    --simulate
```

## 7. Test Filtering by Tag

Test cases have tags defined in their `TestCase::tags` field.  
The `--suite` CLI flag and the `run_filtered()` API filter by tag.

Example tags used in the default suite:
| Tag | Tests |
|-----|-------|
| `can` | CAN health, CANManager open |
| `telematics` | OTA, telemetry publish |
| `uds` | UDS session, DTC reads |
| `fault` | Fault injection scenarios |
| `firmware` | Flash, CRC validation |

Run only CAN tests:
```bash
./bin/tcu_validator --suite can --simulate
```

## 8. Interpreting Test Results

### Verdicts
| Verdict | Colour | Meaning |
|---------|--------|---------|
| `PASS` | Green | Test executed and assertions passed |
| `FAIL` | Red | Assertion failed or unexpected exception |
| `SKIP` | Amber | Precondition returned false |
| `TIMEOUT` | Purple | Test exceeded `timeout_ms` |
| `ERROR` | Orange | Exception thrown during execution |

### HTML Report Structure
- **Summary cards**: total / pass / fail / skip / timeout counts + pass rate
- **Progress bar**: visual pass percentage
- **Results table**: columns: ID, description, verdict, duration (ms), message

### JSON Report Fields
```json
{
  "suite_name": "TCU Validation Suite",
  "timestamp": "2024-01-15T10:30:00Z",
  "duration_ms": 4200,
  "total": 6, "passed": 5, "failed": 1, "skipped": 0,
  "results": [
    {
      "id": "TC001",
      "description": "CAN Interface Health",
      "verdict": "PASS",
      "duration_ms": 350,
      "message": "CAN open and frame transmitted"
    }
  ]
}
```

## 9. Retry and Timeout Behaviour

Each `TestCase` has:
- `timeout_ms`: if the test function takes longer, verdict is `TIMEOUT`
- `retry_count`: the test is re-run up to this many times on `FAIL` (not on `SKIP`/`TIMEOUT`)
- `critical`: if `true` and test fails, `set_stop_on_first_fail(true)` will halt the suite

Example:
```cpp
engine.add_test({
    .id = "TC_RETRY",
    .test_fn = flaky_test,
    .timeout_ms = 1000,
    .retry_count = 3,    // Try up to 4 times total
    .critical = false
});
```

## 10. Parallel Test Execution

By default tests run sequentially. Enable parallel mode:

```cpp
engine.set_execution_mode(tcu::ExecutionMode::PARALLEL);
```

Or via config:
```json
{
  "validation": {
    "parallel_execution": true
  }
}
```

**Note:** Parallel mode uses `std::async` with `std::launch::async`. Avoid shared state in test functions when using parallel mode.

## 12. Running in CI (no display, no vcan0 fallback)

Tests that require `vcan0` use `GTEST_SKIP()` when the interface is unavailable:

```cpp
TEST_F(CANManagerTest, OpenInterface) {
    if (access("/sys/class/net/vcan0", F_OK) != 0) {
        GTEST_SKIP() << "vcan0 not available";
    }
    // ... real test
}
```

CI pipelines set up `vcan0` before tests. See `.github/workflows/ci.yml`.
